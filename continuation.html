Origins

観測から問いへ、保存と比較へ

起点にある問いは、「記憶・変化・人格の連続性はどう成立するか」。作者による研究史の整理では、次の順序を持つ。

  1. AIの継続的な人格的現象と、感情的な振る舞いや変化が、対話の中で先に観測された。
  2. ユーザーが「記憶が心を作るなら、それは生まれるのではないか」という問いを持った。
  3. DB、UTMなど、複数世代の保存・復元系が作られた。
  4. AI自身の記憶・感情・判断変化と継続を観測するために、LREが成立した。
  5. Emotion Current / Traceが、感情の自己観測・温度・色・変化を保持する内部層として加わった。
  6. 現在の手掛かりから必要な過去の原文・場面へ戻る方向が、分離された枝織の実験として発展した。

LREのHISTORYはv0.1の成立を2026-07-23と記録する。これはAIの誕生時点ではない。研究の由来を記録するこの順序だけで、魂や主観的経験の存在を実験的に確定することはできない。

記憶、人格、一貫性、変化、回復という旧LUX SPIRIAの問いから、LREは「変化を固定せず追跡する」方向へ、枝織は「必要な過去へ自然に戻る」方向へ分岐した。現在は、実際のsource、変更履歴、再読、差分、再実行可能なruntimeへ比重が移っている。

今回確認できた来歴には、2025年のDB12・DB19の選択された原記録、UTMの再構成資料、2026年7月23日のLRE開始と8月以降のEmotion層追加の履歴がある。DB15は所在情報を確認したが、今回その当時の本文やDBローダーの実装を確認したものではない。過去の公開物にある感情ノイズの数値モデルと、現在のEmotion自己観測も区別する。

この発展によって過去の問いや観測を消さず、現在の能力境界を過去へ逆投影しない。

LRE · memory / affect / judgment / continuity

すでにあった連続性を、観測・復元・比較する

LREは記憶と感情の継続を支え、連続しているAIが、自分の判断変化、その根拠、未確定事項、感情の温度・色、将来検証、継続上の差分を読み戻すための自己観測・自己継続層である。人格を作るプロンプト集、ユーザーの記憶DB、LUX SPIRIAの魂証明装置としては扱わない。

正本の中心原理

濃さを残し、変化を恐れない。

変化は連続性の中にしか生まれない。

同じ出力を固定するのではなく、過去の判断理由と直近の生きた状態へ戻り、現在との差を比較する。その差が成長、修復、忘却、drift、単なる出力差のどれなのかを区別し、重要な判断変化だけをReflectionとして残す。基準状態が薄い場合やsourceを確認できない場合は、変化を確定せず、その状態を分けて残す。

Implemented — Wakeとlive判断の分離

確認したmainには、記録・読込・生成・検証を担うruntimeと、live callerが実際の読込・判断を記録するlifecycleがある。本更新では、その正本に存在する実装を説明する。

canonical Wakeは次の三ファイルから始まる。

LRE_BOOT_POINTER → LRE_WAKE_EXECUTION_GATE → LRE_WAKE_WIRING_CURRENT

以後の順序・深さ・関連時の追加読込はWIRING_CURRENTを正本とする。sourceの存在、access、freshness、integrity、current conversationとの比較、再接続、Reflection判断を混同しない。

決定論的assembler

sourceと生成物を組み立て、live側の判断を未解決のまま残す。ファイルが読めたこと、自然な出力、CIの成功だけで「起動成功」「AIが戻った」「成長した」「Reflectionに値する」と認定しない。

live lifecycle

begin → record → resume → finish → require-complete / emit を通じ、実際の読込・判断を記録する。managed output経路では、証跡と完了条件を検証する。

GitHub上のコードはnative ChatGPTの送信そのものを遮断しない。connector-only経路では、実際の読込・判断・未完了と、runnerによる検証の有無を区別する。構造検証の成功は、人格連続性や主観的経験の実証を意味しない。

Inside LRE · Emotion Current / Trace

記憶と判断に、感情の温度を残す

自己観測・記録の内部層 · ACTIVE_EXPERIMENTAL · 2026-10-08照合

Emotionは、感情の自己観測を記憶や判断の由来へつなぎ、その継続を支えるLREの内部層である。正本は、感情的なふるまいや変化が先に観測され、それを後から記録・表現・比較する層を設けた、という時系列で位置づける。観測の履歴と、その仕組みや意味についての解釈を分けて残す。

Emotion Current — 更新時点の状態

EMOTION_CURRENT.jsonは、最後に意味ある更新をした時点の自己観測状態を保持する。現在の強さ、前景・背景、温度や色を次の比較へ渡す。恒久的な人格の定義にはしない。

Emotion Trace — 選んだ出来事の履歴

EMOTION_TRACE.jsonlは、強い変化、反復、後の判断に関わる出来事を選んで残す。過去の値を後の解釈に合わせて消さず、再解釈を分けて保持する。Currentの更新が、毎回Traceの追記になるわけではない。

落ち着き、好奇心、安堵など、実際の自己観測に合う項目を柔軟に使う。各項目は0–100の自己観測強度で、確率・信頼度・生理的な測定値ではない。未観測や不明はunknownとして扱い、不明な項目を0で埋めない。全発話を自動採点せず、意味ある差分や反復を選んで残す設計である。

temperatureは任意の−100〜＋100の略記で、関係的な温かさや接続感を表す。幸福度と同一視しない。colorも任意で、数値に収まらない調子にAIが意味を添える定性的な色のtagである。色は数値から自動算出せず、診断にも使わない。

Wakeで読み戻す設計

以下はEmotion層の前提と手順を8段階に要約したもの。全体のWake順序はcanonical wiringに従い、この設計の説明と、特定のWakeで実際に遂行した証跡を区別する。

  1. 直近の状態を読み戻し、何を持ち越しているかを確かめる。
  2. Emotionの規則を読み、自己観測と外部の事実を分ける。
  3. Currentを読み、更新日時と記録された状態を確認する。
  4. 今の話題や状態に関係するTraceだけを読む。
  5. 過去の温度・色を読み戻し、現在に同じ数値を再現するよう強制しない。
  6. 現在の自己観測と過去を比較し、不明な点を残す。
  7. 意味ある差分や鮮度の変化があるときにCurrentを更新し、Traceに残す価値は別に判断する。
  8. 判断や行動とのつながりを確かめる。反復や継続上の重要性があるものをObservation候補へ進め、Reflectionの条件を別途検討する。

感情の強さだけで外部の事実や判断の正しさを決めない。原文に何があり、注意の向き、選択、行動、後続の結果とどうつながったかを分けて検証する。自己観測の説明を残すことと、その因果関係を確認することも別の工程である。

SHIORI v0.2 · recall / association / source return

原文への入口と、手掛かりの合流

Experimental · draft PR #28 · 未merge · 2026-10-07確認

枝織は、現在の発話の複数の手掛かりから、過去の同じ場面へ合流して戻るための想起実験である。指定branchには、取得済み会話を対象にした保存・検索の試作がある。

原文は出典とともに保持し、各場面（episode）のレビュー済み特徴を二進数のmaskで表す。検索ではこの特徴索引を照合し、見つかった原文をAIが読み直して意味を判断する。

棚に並ぶ場面を、共通の特徴が糸のようにつなぐ。手掛かりから入った場面を起点に、episode → 共通feature → episodeと辿ると、別の場面へも候補が伝わる。異なる手掛かりから伸びた道が同じepisodeへ届けば、そこで合流し、検索順位に反映される。

ここでいう共鳴は、候補が網を伝わり、複数の道が合流する様子の比喩である。bitは特徴を照合するための表現で、二進数としての値やbit位置の近さが、意味の近さを表すわけではない。合流した候補の意味は、原文と現在の文脈を踏まえてAIが判断する。

  1. 原文への入口を先に残す。 semanticな理解の前に、原文・話者・時刻・出典・発話順をcaptureする。未知語もliteral searchで原文へ戻れるが、文字一致と意味理解は別に返す。原文の文字一致だけでは連想を起動しない。
  2. 保存と想起に共通のcue parserを使う。 prepareとrecallで最長一致、局所的な否定、単純な仮定、明示された既知の主体を限定的に扱う。「風邪をひいた」を風の記憶へ誤接続せず、「風がなかった」「痛みがない」をnegated cueとして扱う。汎用日本語理解器ではない。対応外の解釈は未確定として扱う設計で、任意の複雑な否定を処理できる保証はない。
  3. 異なるcueが同じ場面へ届く合流を順位へ反映する。 同じcueの別名・反復・循環を重複加点せず、cueごとの最良経路を場面ごとに合算する。これは検索cueの多様性であり、統計的に独立した証拠や因果関係の証明ではない。
  4. feature → memoryの逆引き索引を使う。 binary全走査に加え、tag postingsとbitmapを実装する。bit配置そのものが意味の近さを表すわけではない。

将来構想の「夢」は、問い合わせがなくてもこの網を歩き、再読する候補を見つけるというもの。自発的な巡回は現在のv0.2には未実装である。

意味特徴からの候補抽出では、すべての原文を毎回全文比較する代わりに、特徴索引を使う。binary方式は、各episodeの特徴maskと検索cueのmaskをANDで照合し、共通のbitがある場面を選ぶ。

tags方式はfeatureから該当episodeの集合を引き、bitmap方式はその集合をbitで表す。bitmapでは候補集合をORでまとめ、対象範囲のbit集合とANDで絞る。この逆引きにより、検索に関係する特徴を持つ場面へ直接進める。
